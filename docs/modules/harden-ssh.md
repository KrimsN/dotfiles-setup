# scripts/harden-ssh.sh (`knrc harden-ssh`)

Пошаговый харденинг SSH-сервера **этой** машины: отключает root-логин и
вход по паролю после подтверждённого доступа по ключу. Публичная точка
входа — `harden_ssh::run`, пользовательская — `knrc harden-ssh`.

## Почему отдельная команда, а не модуль install.sh

Зафиксировано пользователем: остальные модули проекта настраивают
окружение разработчика (zsh, tmux, CLI-тулы) — обратимые, низкого риска
изменения, которые откатывает общий `knrc uninstall`. Харденинг SSH —
другого рода вмешательство:

- цена ошибки — потеря доступа к машине по SSH, а не сломанный `.zshrc`;
- у него нет места в `KNRC_ALL_MODULES`/`install.sh`, `knrc doctor` и
  `knrc uninstall` — команда запускается только явно, по образцу
  `modules/zsh-terminal-app.sh` (тоже опционального, вне общего списка),
  но, в отличие от него, не участвует и в общем откате: свой
  `--rollback` вместо `uninstall::_plan_config`.

Полноценный ФСТЭК-хардинг (см. обсуждение репозитория
matveevandrey/fstec-linux-hardening) в проект сознательно не включён —
не подходит по классу задач (сервер/compliance, а не рабочая машина
разработчика) и по зрелости (нет лицензии, один автор, давно без
активности). `harden-ssh` — минимальный набор мер, которые оправданы на
любой корпоративной машине.

## Что делает

Два шага, каждый со своим подтверждением:

1. **Доступ по ключу.** Проверяет `~/.ssh/authorized_keys` текущего
   пользователя. Если ключей нет — печатает инструкцию (`ssh-copy-id`
   с клиента ИЛИ вставить публичный ключ в диалог, тогда скрипт сам
   допишет его с правами `700`/`600`). Проверяет формат ключа (префикс
   `ssh-ed25519`/`ssh-rsa`/`ecdsa-sha2-`/`sk-`). Дальше **обязательно**
   требует подтверждения `yes`, что вход по ключу проверен в НОВОЙ
   сессии — без этого шаг 2 не выполняется.
2. **Применение директив.** Бэкап `/etc/ssh/sshd_config`
   (`<путь>.bak.<YYYYMMDDHHMMSS>` — та же схема имени, что у
   `scripts/lib/backup.sh`, хотя сам файл требует `sudo` и функцию не
   переиспользует), `PermitRootLogin no` и `PasswordAuthentication no`
   (первое совпадение в файле заменяется целиком, иначе директива
   дописывается в конец — то же правило первого совпадения, что у
   `sshd_config`, учтено и в `modules/ssh-config.sh` для клиентского
   `ssh_config`). Обязательная проверка `sshd -t` перед перезагрузкой
   sshd; при ошибке — немедленный откат бэкапа без перезагрузки службы.

Если запущено от root — отдельное предупреждение и подтверждение до
всего остального: харденинг отключит root-логин по SSH, а другого
пользователя с ключом и sudo может не быть.

Если уже захардено (`PermitRootLogin` = `no`/`prohibit-password` и
`PasswordAuthentication` = `no`, читается эффективный конфиг через
`sshd -T`, а не grep по файлу) — сообщает и не делает ничего.

## Откат

`knrc harden-ssh --rollback` — находит самый свежий бэкап
`/etc/ssh/sshd_config.bak.*`, спрашивает подтверждение, восстанавливает
его, проверяет `sshd -t` и перезагружает службу. Не привязан к
`knrc uninstall` — работает и если `harden-ssh` никогда не входил в
установленные `.knrc`-модули.

## Флаги

- `--dry-run` — план без изменений (свой, не через `DRY_RUN` модулей
  install.sh — экспортирует `DRY_RUN` внутри себя).
- `--force` — не спрашивать подтверждений. Обходит и проверку "вход по
  ключу проверен", и предупреждение про root — использовать только при
  полной уверенности в ключе.
- `--rollback` — см. выше.
- `--help`.

## Тестирование

Вручную в disposable-контейнере Ubuntu 24.04 (openssh-server + sudo,
непривилегированный пользователь с NOPASSWD sudo):

- полный интерактивный сценарий (ключ вставлен в диалог, подтверждение
  `yes`) — ключ добавлен в `authorized_keys` с правами `700`/`600`,
  `sshd_config` забэкаплен, `PermitRootLogin no` и
  `PasswordAuthentication no` применены, `sshd -t` прошла, служба
  перезагружена;
- после этого: вход по ключу проходит, вход по паролю и вход под root
  (даже с тем же ключом) — оба отклонены (`Permission denied
  (publickey)`);
- повторный запуск (`--dry-run`) корректно определяет "уже захардено" по
  эффективному конфигу (`sshd -T`) и ничего не делает;
- `--rollback --force` возвращает бэкап, `sshd -t` проходит, служба
  перезагружается, `PasswordAuthentication` снова предлагается сервером;
- без `/dev/tty` (`--dry-run </dev/null`) — ни один `read` не падает
  сырой ошибкой редиректа, шаги вежливо пропускаются с понятным
  сообщением;
- без systemd в PID 1 (сам контейнер) — `harden_ssh::_reload` падает на
  `systemctl` и восстанавливается через `service <svc> restart`,
  подтверждено тем же прогоном.

## Что намеренно не делает

- Не трогает порт SSH, fail2ban, firewall, MFA — это уже не "минимум
  для любой корпоративной машины", а отдельное решение с собственными
  компромиссами, которое стоит настраивать осознанно, а не по умолчанию.
- Не работает с ключами других пользователей, кроме того, от чьего
  имени запущен `knrc harden-ssh`.
