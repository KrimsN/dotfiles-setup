# knrc doctor

Диагностика уже настроенной машины: что из установленного реально на
месте, чего нет и что стоит, но сломано. Отвечает на вопрос, ради
которого команда и появилась — после `install.sh` не было способа
быстро понять состояние машины, кроме как перебирать `command -v`
руками.

Реализация: [`scripts/doctor.sh`](../../scripts/doctor.sh) (диагностика),
[`scripts/knrc.sh`](../../scripts/knrc.sh) (CLI-диспетчер),
[`scripts/lib/modules.sh`](../../scripts/lib/modules.sh) (общий список
модулей), [`scripts/lib/localbin.sh`](../../scripts/lib/localbin.sh)
(`~/.local/bin` в PATH).

## Способ вызова: почему установленная команда `knrc`

Рассматривались три варианта.

| Вариант | Против |
|---|---|
| Подкоманда `install.sh doctor` | `install.sh` — установщик: печатает баннер, вешает EXIT-трап и дописывает строку в `~/.knrc.log` на каждом прогоне. Диагностика — операция чтения, ей всё это не нужно, а отключать по флагу значит завести внутри установщика второй режим работы. Плюс через `curl \| bash` подкоманда доступна только вместе с клонированием репозитория. |
| Отдельный `scripts/doctor.sh` | Работает только из каталога репозитория, который пользователь после `curl \| bash` не открывал и чей путь (`~/.local/share/knrc`) не помнит. Не даёт общего места для будущих `update`/`uninstall` — их пришлось бы звать тремя разными путями. |
| **Установленная команда `knrc`** (выбрано) | Требует, чтобы каталог с командой был в PATH, и ставит на машину ещё один файл. |

Выбран третий вариант в форме **тонкого шима**:

```
~/.local/bin/knrc          — шим на 8 строк: exec bash $REPO/scripts/knrc.sh "$@"
$REPO/scripts/knrc.sh      — диспетчер команд, вся логика здесь
$REPO/scripts/doctor.sh    — реализация doctor
```

Следствия, ради которых схема и выбрана:

- **Обновление** — это `git pull` в каталоге репозитория. Шим содержит
  только путь и не устаревает, копировать бинарник заново не нужно.
  Будущий `knrc update` сводится к «обнови клон и перезапусти
  install.sh», а не к отдельной процедуре самообновления CLI.
- **Без sudo** — `~/.local/bin`, а не `/usr/local/bin`: установка
  команды не требует прав и ничего не кладёт в системные каталоги (что
  важно для будущего `knrc uninstall` — удалять придётся только
  пользовательские файлы).
- **PATH уже управляется проектом.** `~/.local/bin` и так добавлялся
  снипетом `~/.config/knrc/path.sh` ради `uv`/`ruff`. Снипет вынесен из
  `modules/python-tools.sh` в `scripts/lib/localbin.sh`, чтобы у файла
  был один автор: лаунчеру тот же каталог нужен в PATH независимо от
  того, выбран ли модуль python-tools.
- **Из клона тоже работает.** `bash scripts/knrc.sh doctor` запускается
  напрямую, без установки шима — этим и тестируется чистый контейнер,
  где ничего не установлено.

Лаунчер ставит `install_sh::_install_launcher` — не модуль, а часть ядра
установки: `knrc doctor` должен быть на машине при любом наборе
выбранных модулей. `install.sh` подчиняется `DRY_RUN` и здесь.

### Куда лягут `update` и `uninstall`

В `scripts/knrc.sh` — одной веткой `case` и одним файлом
`scripts/<команда>.sh` с публичной функцией `<команда>::run`, ровно как
сейчас устроен `doctor`. Ничего в `install.sh`, лаунчере или PATH при
этом менять не придётся. Заготовки-заглушки в диспетчере сознательно не
оставлены — команда, которая отвечает «пока не реализовано», хуже, чем
её отсутствие.

Для `uninstall` уже подготовлен `rcfile::remove_block`
(`scripts/lib/rcfile.sh`) — сейчас он используется для миграции
переименованного маркера `python-tools-path` → `localbin-path`.

## Что проверяется

Общее (всегда, вне зависимости от `--modules`):

- **система** — дистрибутив/семейство/пакетный менеджер через
  `os::detect`, архитектура, последняя строка `~/.knrc.log` (когда и чем
  завершился последний прогон `install.sh`);
- **PATH** — `/usr/local/bin` и `~/.local/bin` на месте; пустой элемент
  в `PATH` (шелл трактует его как текущий каталог) — единственный тут
  статус «сломано»; несуществующие каталоги упоминаются, но проблемой не
  считаются, шелл их просто пропускает;
- **лаунчер knrc** — сам шим, его исполняемость и то, что репозиторий,
  на который он ссылается, ещё существует (самый вероятный способ
  сломать схему — переместить или удалить клон);
- **login-shell** — читается из passwd, а не из `$SHELL` (тот не
  обновляется до перелогина). Не-zsh это не проблема: смена
  login-shell в проекте опциональна (`ZSH_DEFAULT_SHELL`). «Сломано» —
  только если бинарник login-shell'а не существует.

По модулям — по одной проверке на каждую сущность, которую ставит
соответствующий модуль (все 14 модулей `KNRC_ALL_MODULES`): бинарники в
PATH, конфиги (наличие + маркер `Managed by .knrc` + синтаксис),
клонированные плагины, управляемые блоки в `~/.bashrc`. Отдельно стоит
отметить неочевидные:

- **zsh** — `zsh -n ~/.zshrc`: битый `.zshrc` ломает каждый новый
  терминал, и по одному факту «файл на месте» этого не видно.
  Отсутствие `~/.p10k.zsh` — не проблема, мастер запускается при первом
  интерактивном zsh.
- **tmux** — TPM + три плагина по каталогам; отдельно наличие
  `xclip`/`wl-copy`, без которых tmux-yank молча не копирует.
- **nvim** — `nvim --headless +qa`. Единственная настоящая проверка
  валидности `init.lua`. Кода возврата мало: при ошибке в lua-конфиге
  nvim печатает её и всё равно выходит с 0 по `+qa`, поэтому проверяется
  и вывод.
- **cli-tools** — `fd`/`bat` проверяются с альтернативой
  `fdfind`/`batcat`: если в PATH только переименованный apt-бинарник,
  это статус «сломано» (не отработал `cli::ensure_symlinks`), а не
  «отсутствует».
- **git-config** — `core.pager`/`core.editor` проверяются не на «ключ
  выставлен», а на «бинарник из значения существует»: `core.pager delta`
  без `delta` в PATH ломает вообще любой `git diff`. Зеркально повторено
  и условие самого модуля: `git_config::setup_pager`/`setup_editor`
  намеренно не трогают эти ключи, когда `delta`/`nvim` не установлены,
  поэтому незаполненный ключ — проблема только если бинарник в PATH
  есть; иначе это справочная строка. Без этого doctor ругался бы на
  каждую машину, где просто не выбран модуль cli-tools или nvim — ровно
  тот ложный сигнал, из-за которого диагностику перестают читать.
  Незаполненные `user.name`/`user.email` — «отсутствует» (коммит сделать
  не получится).
- **ssh-config** — права `700`/`600`: с более открытыми ssh сам
  отказывается работать.
- **docker** — недоступный демон и отсутствие пользователя в группе
  `docker` не считаются проблемой (контейнер/WSL без systemd, осознанный
  выбор через `DOCKER_ADD_USER_TO_GROUP`) и выводятся как справка.
- **fonts** — мало файлов на диске: проверяется, что `fc-list` реально
  видит Nerd Font, иначе иконки Powerlevel10k превратятся в квадраты.
  Выбор шрифта в терминальном эмуляторе автоматизировать нельзя — про
  это печатается напоминание.

Модуль `zsh-terminal-app` не покрыт: он не входит в `KNRC_ALL_MODULES`,
ставится только явным запросом и проверять его у всех подряд значило бы
шуметь ложным «отсутствует».

## Вывод и код возврата

Одна строка на проверку, три статуса, никакого своего форматирования:
они ложатся ровно на три уровня `scripts/lib/log.sh`, откуда
наследуются цвет, префикс `[.knrc]` и поведение при `NO_COLOR`/не-терминале.

| Статус | Уровень | Влияние на код возврата |
|---|---|---|
| `ok` | `log::info` (`▶`) | нет |
| `отсутствует` | `log::warn` (`⚠`) | да |
| `сломано` | `log::err` (`✖`) | да |
| справочная строка | `log::info` (`▶`) | нет |

В конце — `ok: N, отсутствует: M, сломано: K`.

- `0` — проблем нет;
- `1` — есть отсутствующее или сломанное (годится как шаг CI);
- `2` — ошибка аргументов (в том числе неизвестное имя в `--modules`;
  имена валидируются до первой проверки, чтобы опечатка не выяснялась
  на середине уже напечатанного отчёта).

`--modules=zsh,tmux` (запятые или пробелы) сужает набор — например
чтобы не получать 60 строк «отсутствует» на машине, где половина
модулей не ставилась намеренно. По умолчанию проверяются все.

## Реальные баги, пойманные при тестировании

- **`pipefail` + `grep -q` = проверка врёт ровно наоборот.** Проверка
  шрифта была написана как `fc-list | grep -qi 'nerd font'`. `grep -q`
  выходит на первом же совпадении и закрывает пайп, `fc-list` получает
  SIGPIPE (141), и `pipefail` делает **весь** конвейер неуспешным — то
  есть условие оказывается ложным именно тогда, когда образец нашёлся.
  На полностью настроенной машине doctor уверенно рапортовал «Nerd Font
  не в кэше», хотя `fc-list` показывал 114 начертаний. Тот же дефект
  сидел ещё в трёх местах (проверка группы `docker`, разбор вывода
  `nvim --headless`, чтение пути из лаунчера). Исправлено переходом на
  here-string (`grep -q ОБРАЗЕЦ <<<"$var"`) и захват вывода в
  переменную — код корректен при любом наборе `set`-опций, а не только
  без `pipefail`. Предупреждение продублировано в шапке
  `scripts/doctor.sh`, чтобы конструкцию не вернули обратно.
- **Отчёт печатался в перемешанном порядке.** `log::info` пишет в
  stdout, `log::warn`/`log::err` — в stderr (конвенция проекта); при
  любом перенаправлении (файл, пайп, лог CI) это разные потоки, и
  «ok»-строка одного модуля оказывалась между «отсутствует»-строками
  соседнего. Для отчёта, где порядок строк и есть содержание, это
  дефект. Исправлено склейкой потоков на верхнем уровне
  (`doctor::run "$@" 2>&1` в `knrc::doctor`), а не правкой `log.sh`.
- **`set -e` из подключаемых библиотек убивал диагностику.**
  `scripts/lib/log.sh` и `os-detect.sh` включают `set -euo pipefail` при
  сорсинге, а для doctor ненулевой код отдельной проверки — штатный
  режим, а не сбой. `knrc::doctor` снимает `-e` перед вызовом
  `doctor::run`; в самом `scripts/doctor.sh` `set -e` не включается.

## Ограничения

Doctor **ничего не чинит и не ставит** — это сознательное ограничение, а
не незаконченность. Диагностика, которая по ходу дела меняет систему,
перестаёт быть воспроизводимой (второй запуск показывает не то же
самое, что первый) и не годится для CI. Чинить — это `install.sh`
(идемпотентен) и будущий `knrc update`; doctor в конце сам печатает
подсказку с нужной командой.

Отсюда же следует, что doctor не проверяет версии: «стоит устаревший
`fzf`» — это задача `knrc update`, а не диагностики.

**Тестирование** (см. скил `test-module`):

1. **Чистый контейнер, ничего не установлено** — `ubuntu:24.04` и
   `quay.io/centos/centos:stream9`, `bash scripts/knrc.sh doctor` из
   смонтированного репозитория. Честно рапортует отсутствие всего
   (64 строки «отсутствует»), не падает ни на одной проверке,
   возвращает `1`.
2. **Контейнер после полной установки** — Ubuntu 24.04,
   `NONINTERACTIVE=1 ./install.sh` со всеми 14 модулями, затем
   `knrc doctor` уже установленной командой (проверяется и сам лаунчер, и
   то, что он нашёлся в PATH): `ok: 89, отсутствует: 3, сломано: 0` —
   незаполненные `user.name`/`user.email` (в контейнере их спросить не у
   кого) и, до исправления бага с `pipefail`, ложное «Nerd Font не в
   кэше». После исправления повторный прогон `base,fonts,docker` даёт
   `отсутствует: 0` и код `0`.
3. **CentOS Stream 9** — `base,aliases,diagnostics,python-tools`, два
   прогона `install.sh` в одном контейнере (идемпотентность), затем
   `knrc doctor`: `ok: 26, отсутствует: 0, сломано: 0`, код `0`.
   Проверяет rhel-семейство (`os::detect`, EPEL-пакеты, `stat`/`getent`).
4. **Статусы и коды возврата** — на Ubuntu 24.04 отдельно
   воспроизведены: битый `~/.zshrc` (ловится `zsh -n`), подменённые
   вручную `~/.zshrc` и `~/.tmux.conf` (нет маркера `Managed by .knrc`),
   `core.pager` на несуществующий бинарник, права `777`/`644` на
   `~/.ssh` — все шесть дают «сломано» и код `1`; неизвестный модуль в
   `--modules` и неизвестная команда — код `2`; `--help` — код `0`.
5. **`--dry-run`** — после прогона ни `~/.local/bin/knrc`, ни
   `~/.config/knrc/path.sh`, ни блок в `~/.bashrc` не созданы.
6. **Идемпотентность и миграция маркера** — два прогона `install.sh`
   (`base zsh tmux aliases git-config ssh-config python-tools`) в одном
   контейнере: лаунчер остаётся исполняемым, а заранее подложенный
   старый блок `knrc:python-tools-path` в `~/.bashrc` исчезает, новый
   `knrc:localbin-path` присутствует ровно в одном экземпляре.
7. **Отсутствие ложных срабатываний git-config** — на машине без
   `delta`/`nvim` `core.pager`/`core.editor` дают справочные строки и код
   `0`; после появления `delta` в PATH тот же незаполненный
   `core.pager` становится «отсутствует» и даёт код `1`.
