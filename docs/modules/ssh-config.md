# modules/ssh-config.sh

Настраивает клиентский `~/.ssh/config`. Публичная точка входа —
`ssh_config::install`.

## Зачем

На свежей машине без клиентского `~/.ssh/config` SSH-сессии молча
отваливаются по таймауту (нет keepalive до NAT/файрвола), а ключи,
добавленные в агент, не подхватываются автоматически.

## Что выставляется

Блок `Host *`:

| Ключ | Значение |
|---|---|
| `ServerAliveInterval` | `60` |
| `ServerAliveCountMax` | `3` |
| `TCPKeepAlive` | `yes` |
| `AddKeysToAgent` | `yes` |
| `HashKnownHosts` | `no` |

`HashKnownHosts no` — осознанный компромисс, не упущение: по умолчанию
ssh хэширует хосты в `known_hosts`, из-за чего файл нельзя ни
прочитать, ни вручную поправить (например удалить одну строку при
смене хоста) без `ssh-keygen -R`. На однопользовательской машине
приватность списка хостов не перевешивает удобство ручной правки.

## Почему `rcfile::upsert_block`, а не запись файла целиком

В отличие от `~/.gitconfig` (модуль `git-config`, ключи через `git
config`) и `~/.tmux.conf` (копирование файла целиком с бэкапом),
`~/.ssh/config` почти наверняка уже содержит собственные Host-блоки
пользователя (ключ/порт/прокси под конкретный хост) — их нельзя
затирать. Модуль переиспользует `scripts/lib/rcfile.sh`
(`rcfile::upsert_block`), тот же механизм, что у хуков tmux-autoattach
и aliases: блок обрамляется маркерами `# >>> knrc:ssh-config >>>` /
`# <<< knrc:ssh-config <<<`, при повторном запуске старое содержимое
между маркерами удаляется и блок пишется заново.

**Порядок в файле критичен**: в ssh_config для большинства опций
выигрывает первое совпадающее значение по каждому ключу — значит наш
`Host *` обязан идти в конце файла, иначе он перебьёт пользовательские
Host-блоки, объявленные выше. `rcfile::upsert_block` всегда удаляет
старый блок и дописывает новый в конец файла — это свойство, на
котором и держится корректность модуля, а не побочный эффект.

## Права доступа

`~/.ssh` — `700`, `~/.ssh/config` — `600` (выставляются безусловно при
каждом запуске, до и после записи блока) — иначе сам ssh откажется
использовать файл/каталог.

## Тестирование

`base,ssh-config` на Ubuntu 24.04 через `.claude/skills/test-module/`
(`scripts/test-module.sh base,ssh-config ubuntu24`), два прогона в
одном контейнере — прошли без ошибок.

Отдельно, вручную в том же образе — сценарий «чужое содержимое»:

- файл `~/.ssh/config` заранее заполнен посторонним `Host myhost`
  (`HostName`/`User`/`Port`) с правами `700`/`600`;
- после первого прогона `ssh_config::install` чужой блок остался без
  изменений и идёт ПЕРЕД добавленным `Host *`; права `700`/`600`
  сохранены;
- второй прогон (идемпотентность): наш блок не задублирован
  (`grep -c "Host \*"` = 1), чужой блок по-прежнему цел и по-прежнему
  идёт первым;
- `ssh -G myhost` подтверждает, что специфичные `user deploy`/
  `port 2222` из чужого блока не перебиты нашим `Host *`, при этом
  `serveraliveinterval 60`/`addkeystoagent true` из `Host *`
  применились и к `myhost`, и к произвольному `otherhost` без
  собственного блока — ssh_config комбинирует первое совпадение по
  каждому отдельному ключу, а не блок целиком.
