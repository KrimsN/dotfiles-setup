# modules/zsh.sh

Устанавливает zsh (через `os::pkg_install`), oh-my-zsh (неинтерактивно:
`RUNZSH=no CHSH=no`), Powerlevel10k и три внешних плагина
(zsh-autosuggestions, fast-syntax-highlighting, zsh-completions) через
`git clone --depth=1` в `$ZSH_CUSTOM`, пишет `~/.zshrc` из `config/zshrc`
(с бэкапом старого файла при отличии — сравнение через `cmp`; т.к.
`diffutils` не всегда стоит в минимальных образах, модуль сам ставит его
перед сравнением через `os::pkg_install diffutils`, идемпотентно) и
опционально делает zsh login-shell'ом по умолчанию через `chsh` — вопрос
задаётся через `/dev/tty` (`zsh::_want_default_shell`) по схеме из
"Механизм конфигурации" в CLAUDE.md, с env-override
`ZSH_DEFAULT_SHELL=yes|no` и безопасным дефолтом "no" без интерактива.

Требует зависимость `scripts/lib/os-detect.sh` (использует
`os::pkg_install`) — подключать оба через `source` в этом порядке.
Идемпотентен: повторный запуск ничего не переустанавливает и не трогает
уже применённый login-shell (проверка через `getent passwd`, а не
`$SHELL`, т.к. переменная не обновляется до перелогина).

`config/zshrc` дополнительно содержит (сверено с рабочим `~/.zshrc` из
реальной WSL-настройки):
- кэш автодополнения (`zstyle ':completion:*' use-cache on` +
  `cache-path`), выставляется до `compinit` (запускается внутри
  `oh-my-zsh.sh`);
- расширенные настройки истории (`HISTSIZE`/`SAVEHIST=50000`, общая
  история между сессиями, дедупликация, поиск по префиксу на
  стрелках вверх/вниз), плюс `HIST_IGNORE_SPACE` (команды с ведущим
  пробелом не пишутся в историю) и `HIST_REDUCE_BLANKS`;
- `AUTO_CD`, `INTERACTIVE_COMMENTS`, `EXTENDED_GLOB`;
- биндинги Home/End/Delete и Ctrl+стрелки (переход по словам).
  Сначала пробуем `terminfo[khome]`/`kend`/`kdch1` — это единственный
  способ получить правильную последовательность для реального `$TERM`
  (критично в tmux/SSH, где `$TERM` меняется на `screen-256color` /
  `tmux-256color`, и захардкоженные xterm-коды вроде `\e[H` там не
  всегда совпадают). Поверх — набор сырых escape-последовательностей
  как fallback на случай неполной terminfo-записи (xterm/screen, VT220,
  rxvt/urxvt дают разные коды). Для Ctrl+стрелок terminfo обычно вообще
  не содержит capability, поэтому там сразу зашит набор вариантов;
- `EDITOR`/`VISUAL` — `nvim`, если он поставлен модулем `nvim.sh`
  (`command -v nvim`), иначе `vim`, иначе переменные не трогаются;
  `PAGER=less`, `LESS='-R -F -X'` (цвета delta/bat как есть, авто-выход
  на однострочном выводе, не чистить экран после выхода);
- интеграция fzf/zoxide с шеллом, guard'ится через `command -v` (не
  зависит от того, ставился ли `cli-tools.sh`). Для fzf — двухступенчатый
  фолбэк: сначала пробует `fzf --zsh` (флаг появился в fzf 0.48, 2024),
  и только если бинарник его не поддерживает (например версия из apt на
  Ubuntu 24.04/Debian 12 — там `0.44.1`), source'ит пакетные скрипты
  `/usr/share/doc/fzf/examples/{key-bindings,completion}.zsh`. В
  минимальных Docker-образах (`ubuntu:24.04` и т.п.) эти файлы вырезаны
  дистрибутивом ради размера образа — тогда fzf остаётся без байндингов,
  но шелл стартует без ошибок; на реальной машине (проверено на WSL
  Ubuntu) файлы есть и биндинг `^R` → `fzf-history-widget` подключается.

**Тестирование**: end-to-end в контейнерах Ubuntu 24.04 и Fedora 39,
включая двойной запуск для проверки идемпотентности. Отдельно
перепроверено (2026-08-25, Ubuntu 24.04, модули `base cli-tools aliases
zsh`) после добавления истории/кэша/fzf-zoxide: двойной прогон
`install.sh`, чистый `zsh -ic` без вывода на stderr, `type z` находит
функцию zoxide, `$(fzf --zsh)` корректно проваливается в fallback на
apt-версии 0.44.1.

Отдельно перепроверено (2026-08-25, Ubuntu 24.04, модули `base zsh`)
после добавления опций шелла/биндингов Home-End-Delete-Ctrl+стрелки/
`EDITOR`-`VISUAL`-`PAGER`-`LESS`: `zsh -n ~/.zshrc` проходит без ошибок,
двойной прогон `install.sh` в одном контейнере идемпотентен, `zsh -ic
exit` не пишет в stderr, `bindkey` в интерактивной сессии подтверждает
регистрацию всех новых биндингов — и terminfo-вариантов (`^[OH`, `^[OF`
для `TERM=xterm-256color`), и всех fallback-последовательностей.

## Точка расширения: `~/.zshrc.local`

`~/.zshrc` перезаписывается install.sh при каждом запуске (с бэкапом, но
всё равно) — держать свои правки прямо в нём нельзя, они не переживут
повторную установку. Публичный контракт: `config/zshrc` в самом конце
подключает `~/.zshrc.local`, если он существует (`[[ ! -f ... ]] ||
source ...`, тот же стиль, что у tmux-autoattach/aliases/path).

`zsh::create_local_file` (вызывается из `zsh::install` сразу после
`zsh::write_zshrc`) создаёт `~/.zshrc.local` с поясняющим комментарием,
если его ещё нет — но **только если нет**: при повторном запуске
install.sh существующий файл не трогает и не перезаписывает, так что
пользовательские правки внутри него переживают любое число переустановок.
Игнорируется git'ом через общий паттерн `*.local` в `.gitignore`.

## Шаблонный `~/.zshrc` от установщика oh-my-zsh (2026-08-25)

`KEEP_ZSHRC=yes`, с которым запускается установщик oh-my-zsh, значит «не
перезаписывай **существующий** `~/.zshrc`», а не «не создавай». На
свежей машине файла нет — и установщик кладёт свой шаблон. Дальше
`zsh::write_zshrc` видит «файл есть и отличается» и делает бэкап
**чужого шаблона**, приняв его за конфиг пользователя.

Пока отката не было, это выглядело просто как мусорный
`~/.zshrc.bak.<время>` в `$HOME` после каждой установки на чистой
машине. С приходом `knrc uninstall` ([uninstall.md](uninstall.md)) у
бага появилось второе, серьёзное последствие: откат честно
восстанавливал этот шаблон — и оставлял на машине `~/.zshrc`, который
сорсит уже удалённый `~/.oh-my-zsh`, то есть ломал каждый новый
терминал.

Исправлено в `zsh::install_oh_my_zsh`: запоминаем, был ли `~/.zshrc` до
запуска установщика, и убираем шаблон, если своего файла не было.
`write_zshrc` после этого видит чистое поле, бэкап не создаётся, а
`uninstall` корректно **удаляет** наш `~/.zshrc` вместо восстановления
чужого.

## Запись прежнего login-shell (2026-08-25)

`zsh::configure_shell` перед `sudo chsh` записывает текущий shell через
`state::record login-shell.prev`
([scripts/lib/state.sh](../../scripts/lib/state.sh)). В passwd потом
видно только «сейчас zsh»; стоял ли он там до установки, из системы уже
не узнать — а `knrc uninstall` обязан вернуть login-shell ровно тот, что
был. Запись делается только в той ветке, где смена реально происходит,
и уважает `DRY_RUN`.

На машинах, настроенных версией без записи состояния, откат login-shell
не трогает и пишет в отчёт готовую команду `chsh` — молча оставить zsh
или молча сменить его на bash одинаково плохо.

## Отсутствие `chsh` на минимальных образах (2026-08-26)

`sudo chsh -s ...` падал с `chsh: command not found` на урезанных
образах: начиная с util-linux 2.36 `chsh`/`chfn`/`newgrp` вынесены из
`util-linux` в отдельный пакет `util-linux-user` (Fedora, RHEL8+/CentOS
Stream/Rocky/Alma) — на минимальных Docker-образах он не входит в
base-набор. На Debian/Ubuntu `chsh` живёт в `passwd` (обычно уже стоит,
но не гарантировано на урезанных образах). На старых RHEL7/CentOS7 (там
только `yum`, `dnf` нет) `chsh` остаётся в `util-linux` — отдельного
`-user`-пакета там ещё не было.

Исправлено защитной установкой `zsh::_ensure_chsh` (тот же паттерн, что
`pkg_registry::_ensure_jq` для `jq`): проверяет `command -v chsh`, и
если бинарника нет — ставит нужный пакет по `PKG_MANAGER` (`passwd` для
`apt`, `util-linux-user` для `dnf`, `util-linux` для `yum`). Вызывается
из `zsh::configure_shell` перед `sudo chsh`, только в ветке, где смена
login-shell реально происходит (после ответа "да" на вопрос и до
проверки `DRY_RUN`... фактически после `DRY_RUN`-выхода, так что при
`--dry-run` пакет не ставится).
