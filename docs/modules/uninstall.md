# knrc uninstall

Откат установки: вернуть машину к состоянию до `install.sh`. Отвечает на
вопрос, который до этого висел открытым — модули делали бэкапы
перезаписываемых файлов, но восстановить всё обратно было нечем.

Реализация: [`scripts/uninstall.sh`](../../scripts/uninstall.sh) (весь
откат), [`scripts/knrc.sh`](../../scripts/knrc.sh) (CLI-диспетчер),
[`scripts/lib/state.sh`](../../scripts/lib/state.sh) (запись прежнего
login-shell и членства в группе docker),
[`scripts/lib/rcfile.sh`](../../scripts/lib/rcfile.sh)
(`rcfile::remove_block`).

Способ вызова — тот же, что выбран для `doctor` (см.
[doctor.md](doctor.md), раздел «Куда лягут `update` и `uninstall`»):
одна ветка `case` в `scripts/knrc.sh` и один файл `scripts/<команда>.sh`
с публичной функцией `<команда>::run`. Ничего в `install.sh`, лаунчере
или PATH менять не пришлось.

```bash
knrc uninstall --dry-run          # показать план, ничего не менять
knrc uninstall                    # спросит подтверждение и выполнит
knrc uninstall --force            # без вопроса (для автоматизации)
knrc uninstall --modules=zsh,tmux # откатить только эти модули
```

Из клона то же самое доступно как `bash scripts/knrc.sh uninstall`, без
установки лаунчера.

## Две фазы: план, потом выполнение

Команда сначала строит **план** — массив действий, который печатается
целиком, — и только потом, после подтверждения, его проигрывает.

Из этого следует главное свойство: `--dry-run` это буквально первая фаза
без второй, а не отдельная ветка кода со своими `if`. План, который
пользователь видит перед вопросом «точно удалять?», и есть ровно то, что
будет выполнено. У описания действия один источник
(`uninstall::_describe`), поэтому строка «что собираемся сделать» и
строка «что сделали» не могут разойтись по смыслу.

Это отличается от того, как `DRY_RUN` устроен в `install.sh`, где он
перехватывается в общих точках мутации `scripts/lib/*` и покрывает не
100% случаев (см. [install.md](install.md)). Здесь покрытие полное по
построению: в режиме dry-run фаза выполнения просто не наступает.

## Подтверждение

Требование к команде, которая удаляет окружение: случайно запустить её
должно быть нельзя.

- **Интерактивно** — вопрос через `read ... < /dev/tty` (а не stdin, по
  общему для проекта соображению из CLAUDE.md). Ответ — слово `yes`
  целиком, не `[y/N]`: цена случайного нажатия здесь слишком велика для
  одной буквы.
- **`NONINTERACTIVE=1` сам по себе подтверждением НЕ считается.** Если
  спросить негде, а явного флага нет — команда отказывается работать с
  кодом возврата 3, а не «молча сносит по умолчанию».
- **`--force`** (или `KNRC_UNINSTALL_FORCE=1`) — явное подтверждение для
  автоматизации.
- **`--yes` отвергается с подсказкой.** У `install.sh` он значит «не
  задавай вопросов, бери дефолты», и рука тянется передать его и сюда.
  Дефолт удаления — не удалять, поэтому флаг с таким смыслом принимать
  нельзя; вместо этого — понятная ошибка с указанием на `--force`.

Наличие `/dev/tty` проверяется попыткой его открыть, а не через
`[ -r /dev/tty ]`: в контейнере без выделенного терминала файл
существует и проверку `-r` проходит, а открытие падает с «No such device
or address» (тот же случай разобран в `modules/git-config.sh`).

## Как решается, «наш» ли файл

Установка меняет пользовательские файлы тремя разными способами, и откат
у каждого свой.

| Способ установки | Кто так делает | Откат |
|---|---|---|
| Копирование поверх с бэкапом | `zsh::write_zshrc`, `tmux::write_config`, `nvim::write_config`, `cli::write_bat_config` | вернуть самый свежий бэкап; если бэкапа нет (файла до нас не было) — удалить файл |
| Маркированный блок в чужом файле | `rcfile::upsert_block` в `~/.bashrc`, `~/.ssh/config` | `rcfile::remove_block` |
| Ключи `git config --global` | `modules/git-config.sh` | снять ровно свои ключи, и только если значение всё ещё наше |

### Схема имени бэкапа

Все четыре копирующих модуля используют **одну и ту же** схему:

```
<путь>.bak.<YYYYMMDDHHMMSS>
```

Это проверялось перед реализацией: расхождений между модулями нет,
поэтому в `uninstall` нет ни разбора вариантов, ни таблицы «у кого какая
схема» — один глоб `"$dest".bak.*` и один `tail -n1`. Лексикографический
порядок глоба совпадает с хронологическим, потому что время записано
как `YYYYMMDDHHMMSS` без разделителей.

Схема зафиксирована в одном месте: `backup::create_if_diff <src> <dest>
<label>` в [scripts/lib/backup.sh](../../scripts/lib/backup.sh).
`zsh::write_zshrc`, `tmux::write_config`, `nvim::write_config` и
`cli::write_bat_config` зовут её вместо того, чтобы формировать имя
бэкапа каждый сам — новый модуль, которому нужен тот же паттерн
(бэкап + перезапись при расхождении), получает верную схему имени
по построению, а не по внимательности автора.

### Правило «трогаем только своё»

Файл из первой строки таблицы удаляется или перезаписывается бэкапом,
только если он **всё ещё наш**: побайтово совпадает с версией из
`config/` **или** содержит маркер `.knrc`. Проверка двойная, потому что
одного `cmp` мало — репозиторий мог обновиться после установки, и файл
на диске законно отстанет от `config/`.

Файл, который пользователь правил руками, не удаляется и не
перезаписывается — он попадает в список «осталось в системе».

Это же правило делает **повторный запуск** `knrc uninstall`
безопасным. Бэкап при восстановлении именно перемещается (`mv`), а не
копируется: после возврата он перестаёт быть бэкапом. Второй прогон
видит на месте конфига пользовательский файл без нашего маркера — и не
трогает его.

## Чего uninstall не делает

- **Не удаляет пакеты пакетного менеджера.** Они могли стоять до нас или
  быть нужны системе (`git`, `curl`, `vim`, `unzip`, `diffutils`).
  Вместо этого в конце печатается список того, что реально установлено,
  с готовой командой удаления под текущий менеджер (`apt-get purge` /
  `dnf remove` / `yum remove`). В список попадают только фактически
  установленные пакеты (`dpkg-query` / `rpm -q`): перечень из полутора
  десятков имён, половины которых на машине нет, читать не будут.
- **Не трогает `*.local`-файлы** — `~/.zshrc.local`,
  `~/.tmux.conf.local`, `~/.config/knrc/aliases.local.sh`. Это точки
  расширения, их содержимое принадлежит пользователю. Они перечисляются
  в «осталось» с командой удаления, но сама команда их не трогает.
- **Не удаляет каталог репозитория** — из него прямо сейчас выполняется
  этот код, и он мог быть склонирован пользователем вручную в рабочий
  каталог. Путь и команда — в «осталось».
- **Не трогает пользовательские данные**: `~/.zsh_history`,
  `~/.p10k.zsh` (ответы мастера), `~/.tmux/resurrect` (сохранённые
  сессии), `~/.local/state/nvim` (shada, история).
- **Не удаляет стандартные XDG-каталоги** (`~/.config`, `~/.cache`,
  `~/.local/share`), даже если после отката они опустели: это не наши
  артефакты.

## Что откатывается по модулям

Ниже — только то, что неочевидно; полный перечень действий всегда
показывает `knrc uninstall --dry-run` на конкретной машине.

**Ядро** (лаунчер `~/.local/bin/knrc`, снипет `~/.config/knrc/path.sh`,
блок `localbin-path` в `~/.bashrc`, `~/.knrc.log`, каталог состояния)
откатывается только при **полном** прогоне. С `--modules=...` ядро не
трогается: частичный откат не должен уносить команду `knrc`.

- **zsh** — `~/.oh-my-zsh` целиком (powerlevel10k и внешние плагины
  лежат внутри, отдельных действий не нужно), `~/.zshrc` по общему
  правилу, login-shell (см. ниже). Дополнительно удаляются кэши, которые
  создают именно наши плагины и которые без них бесполезны:
  `~/.cache/gitstatus` (бинарник gitstatusd, десятки мегабайт, p10k
  качает его себе сам) и `~/.cache/fsh` (тема
  fast-syntax-highlighting). Кэши самого zsh (`~/.zsh/cache`,
  `~/.zcompdump*`) — в список, а не в удаление: если zsh остаётся на
  машине, они ему пригодятся и пересоздадутся сами.
- **tmux** — TPM и три плагина из нашего `tmux.conf` поимённо, а не весь
  `~/.tmux/plugins`: чужие плагины там трогать нельзя. Каталоги
  `~/.tmux/plugins` и `~/.tmux` удаляются, только если опустели.
- **nvim** — `/usr/local/bin/nvim`, `/usr/local/lib/nvim`,
  `/usr/local/share/nvim`. Модуль распаковывает релизный архив целиком в
  `/usr/local`, точного списка файлов не сохранялось, поэтому удаляются
  три пути, которые заведомо принадлежат только neovim; про возможные
  остатки (man-страница, `.desktop`, иконки) пишется в «осталось» с
  готовой командой `ls`. Если `nvim` найден, но не в `/usr/local/bin`,
  он поставлен не нами и не трогается вовсе.

  Отдельный вопрос — всё, что nvim насоздавал вокруг себя: плагины
  lazy.nvim, парсеры treesitter в `~/.local/share/nvim/tree-sitter-*`,
  `lazy-lock.json` и скомпилированный luac-кэш `~/.cache/nvim` (сотни
  файлов). Всё это существует только потому, что мы положили свой
  `init.lua`, поэтому удаление привязано к одному вопросу: **наш ли ещё
  `init.lua`** (та же проверка `_is_ours`, что и для конфигов). Заменил
  пользователь конфиг своим — это уже его хозяйство, и ни плагины, ни
  парсеры не трогаются. `~/.local/state/nvim` не удаляется никогда: там
  shada (метки, регистры, история команд и открытых файлов) — результат
  работы пользователя, переживающий смену конфига.
- **cli-tools / extras / diagnostics** — бинарник в `/usr/local/bin`
  положили мы сами (github-метод реестра), его удаляем; всё, что пришло
  из пакетного менеджера, идёт в «осталось». Путь однозначно указывает
  на источник: пакетный менеджер кладёт бинарники в `/usr/bin`.
  Симлинки `fd -> fdfind` и `bat -> batcat` (см. `cli::ensure_symlinks`)
  снимаются тем же действием — они лежат там же и под теми же именами.
- **git-config** — снимаются только ключи со **своим** значением. Если
  пользователь после установки поменял, например, `pull.rebase`, это уже
  его настройка: ключ остаётся, а строка про него уходит в «осталось».
  `user.name`/`user.email` не трогаются ни при каких условиях — это
  данные пользователя, `install.sh` их только спрашивал.
- **docker** — движок не удаляется (ставился официальным скриптом
  `get.docker.com`), в «осталось» уходит команда удаления пакетов и
  подсказка про `/var/lib/docker`. Из группы `docker` пользователь
  выводится только по записи состояния (см. ниже).

## Запись состояния: чего нельзя узнать из системы

Почти всё, что делает `install.sh`, откатывается по следам: маркер в
файле, бэкап рядом, блок `# >>> knrc:... >>>`. Но два изменения следа не
оставляют:

- смена login-shell (`chsh -s zsh`) — в passwd видно только «сейчас
  zsh»; стоял ли он там до нас, из системы уже не узнать;
- членство в группе docker (`usermod -aG docker`) — то же самое.

Без записи прежнего значения у `uninstall` остаётся выбор из двух
плохих: не трогать вовсе (машина остаётся недоочищенной) или угадывать
(и сломать окружение тому, у кого zsh стоял и до нас). Поэтому появился
[`scripts/lib/state.sh`](../../scripts/lib/state.sh): модуль, делающий
необратимо-неотличимое изменение, пишет прежнее состояние в
`~/.config/knrc/state/<имя>`, а `uninstall` откатывает **только** то,
что там записано. Формат сознательно примитивный — один факт = один файл
с одной строкой: файлов единицы, и читать их должен уметь человек
`cat`-ом, разбираясь, почему откат повёл себя так.

Записи делают `zsh::configure_shell` (`login-shell.prev`) и
`docker::configure_user_group` (`docker-group.added`), обе — только в
той ветке, где изменение реально происходит.

**Машины, настроенные версией без записи состояния**, обрабатываются
явно: если login-shell сейчас `zsh`, а записи нет, `uninstall` не меняет
его и пишет в «осталось» строку с готовой командой `chsh -s /bin/bash`.
Молча оставить zsh или молча сменить его на bash — оба варианта хуже.

## Единый источник списков

`uninstall` подключает `modules/cli-tools.sh`, `modules/diagnostics.sh`,
`modules/extras.sh`, `modules/git-config.sh` и
`modules/zsh-terminal-app.sh` — не ради их функций, а ради констант:
`CLI_PACKAGES`, `DIAGNOSTICS_PACKAGES`, `EXTRAS_PACKAGES`, таблиц
`GIT_CONFIG_*` и `ZSH_TERMINAL_APP_DESKTOP_ID`. Подключение безопасно:
на верхнем уровне у этих файлов только объявления.

Причина та же, по которой существует `scripts/lib/modules.sh` (см.
[modules-list.md](modules-list.md)): разъехавшиеся списки означают, что
часть установленного не попадёт ни в удаление, ни даже в отчёт
«осталось». Ради этого в `modules/extras.sh` появился
`EXTRAS_PACKAGES` (был инлайн двумя вызовами), а ключи
`~/.gitconfig` в `modules/git-config.sh` переехали из тел функций в
таблицы `GIT_CONFIG_DEFAULTS` / `GIT_CONFIG_PAGER` / `GIT_CONFIG_EDITOR`.

Имена системных пакетов и имена бинарников github-метода читаются прямо
из реестра `data/packages/methods/{pkg,github}.json` через `jq` — второй
копии этих таблиц в `uninstall.sh` нет. Если `jq` на машине нет,
команда не падает: она один раз предупреждает и пишет в «осталось», что
список пакетов неполон.

## `zsh-terminal-app` — единственный способ его убрать

Модуль не входит в `KNRC_ALL_MODULES` (ставится только явно), и `doctor`
его не проверяет. В `uninstall` он тем не менее поддержан — через
`--modules=zsh-terminal-app`, — потому что иначе `.desktop`-файл и
перевешенный хоткей Ctrl+T остались бы на машине навсегда. Слот
`gsettings` ищется по имени `Zsh Terminal` с верхней границей перебора:
слоты нумеруются подряд, и без границы цикл по несуществующим `customN`
бесконечен.

## Реальные баги, найденные при тестировании

Все три поймал round-trip-прогон в контейнере, не чтение кода.

### 1. Шаблонный `~/.zshrc` от установщика oh-my-zsh — и битый конфиг после отката

`KEEP_ZSHRC=yes` у установщика oh-my-zsh значит «не перезаписывай
**существующий** `~/.zshrc`», а не «не создавай». На свежей машине файла
нет, установщик кладёт свой шаблон, и дальше `zsh::write_zshrc` видит
«файл есть и отличается» — и делает бэкап **чужого шаблона**, приняв его
за конфиг пользователя.

Последствий два, и второе серьёзное:

- после каждой установки в `$HOME` оставался мусорный
  `~/.zshrc.bak.<время>`, которого никто не просил;
- `knrc uninstall` честно восстанавливал этот шаблон — и оставлял на
  машине `~/.zshrc`, который сорсит уже удалённый `~/.oh-my-zsh`, то
  есть ломает каждый новый терминал.

Чинить это на стороне отката (эвристикой «а не шаблон ли это
oh-my-zsh») было бы лечением симптома. Исправлено в
`zsh::install_oh_my_zsh`: запоминаем, был ли `~/.zshrc` до запуска
установщика, и убираем шаблон, если своего файла не было. Дальше
`write_zshrc` видит чистое поле, бэкап не создаётся, `uninstall`
корректно удаляет наш `~/.zshrc` вместо восстановления чужого.

### 2. `pip3 show` находит и системный пакет — попытка снести httpie из apt

`httpie` ставится pip-методом, только если пакета нет в репозиториях.
Проверка «а ставили ли мы его через pip» была написана как
`pip3 show httpie`, но pip видит и системный пакет из `dist-packages`.
На Ubuntu 24.04, где `httpie` пришёл из apt, откат пытался снять его
через pip и падал с ошибкой PEP 668
(`externally-managed-environment`) — то есть `uninstall` покушался на
системный пакет, чего делать не должен по определению.

Признак **нашей** установки — `Location` внутри `$HOME`: туда кладёт
`pip3 install --user`. Проверка переписана на чтение `Location`;
apt-версия теперь просто уходит в «осталось» вместе с остальными
пакетами.

### 3. `rcfile::remove_block` копил пустые строки

`rcfile::upsert_block` дописывает перед блоком пустую строку, а
`remove_block` снимал только сам блок. После отката в `~/.bashrc`
оставалось по пустой строке за каждый снятый блок — а `uninstall`
снимает их сразу три. Файл не возвращался к исходному виду, и повторные
циклы install/uninstall копили пустые строки дальше.

Исправлено в `remove_block`: вместе с блоком снимается ровно одна пустая
строка непосредственно перед ним. Подряд идущие пустые строки
пользователя при этом сохраняются — придерживается только одна, и только
если сразу за ней идёт наш маркер. Проверено: после
`upsert → upsert → remove → remove` файл побайтово совпадает с исходным.

## Тестирование

Сценарий вынесен в [`scripts/test-uninstall.sh`](../../scripts/test-uninstall.sh)
(тот же стиль, что у `scripts/test-module.sh`), чтобы прогон
переиспользовался между сессиями, а не собирался заново руками:

```bash
scripts/test-uninstall.sh <distro> [<module>[,<module>...]]
```

Внутри одного одноразового контейнера:

1. **снимок чистой машины** — дерево `$HOME` (до 4 уровней),
   `/usr/local/bin`, login-shell из passwd, `git config --global -l`,
   содержимое `~/.bashrc`;
2. подкладывается **свой `~/.tmux.conf`**, отличный от нашего — чтобы
   в прогоне участвовала и ветка «бэкап есть, восстановить», а не только
   «бэкапа нет, удалить»;
3. `install.sh` с `ZSH_DEFAULT_SHELL=yes` (иначе ветка смены login-shell
   не выполняется и откат её не проверяет);
4. **снимок после установки**;
5. `knrc uninstall --dry-run` → **снимок** → diff со снимком (4).
   Расхождение здесь — **провал теста**: dry-run обязан не менять
   ничего;
6. `knrc uninstall --force` → **снимок** → diff со снимком (1) и
   отдельная проверка, что `~/.tmux.conf` вернулся дословно.

Второй diff печатается, но не считается провалом: часть расхождений
ожидаема и описана выше (пакеты, `*.local`, пользовательские данные).
Читать его — и есть содержание теста. На прогонах выше он сошёлся до
ровно ожидаемого набора: `*.local`-файлы, `~/.gitconfig` с пустыми
секциями, история и кэши zsh, shada nvim и пустые XDG-каталоги
(`~/.config`, `~/.cache`, `~/.local/share`). `/usr/local/bin` пуст,
login-shell вернулся на `/bin/bash`, `~/.bashrc` совпадает с исходным
побайтово.

Именно этот diff и заставил довести три вещи до конца: он показал
оставшийся `~/.zshrc` от чужого шаблона (баг 1 ниже), лишние пустые
строки в `~/.bashrc` (баг 3) и две сотни файлов nvim-кэша, которые
сначала не удалялись. Пока такой diff не прочитан глазами, откат нельзя
считать проверенным.

Покрытые дистрибутивы:

| Дистрибутив | Набор модулей | Что проверено |
|---|---|---|
| Ubuntu 24.04 | по умолчанию | полный round-trip, 58 шагов без ошибок; здесь пойманы все баги ниже; ветка `dpkg-query`; ветка «бинарник из apt → в список, а не в удаление» |
| Fedora latest | по умолчанию | полный round-trip на rhel-семействе, 56 шагов без ошибок; ветка `rpm -q`; другие имена пакетов из реестра (`bind-utils` вместо `dnsutils`, `mtr` вместо `mtr-tiny`) |
| Ubuntu 24.04 | `base,nvim,cli-tools,git-config` | 38 шагов без ошибок; удаление распакованного в `/usr/local` neovim (`bin/`, `lib/`, `share/`) — `/usr/local/bin` после отката пуст; плагины, парсеры treesitter и luac-кэш вычищены |

Отдельно, без round-trip-скрипта, проверены ветки подтверждения и
аргументов (Ubuntu 24.04, набор `base aliases ssh-config`):

| Сценарий | Ожидание | Результат |
|---|---|---|
| `NONINTERACTIVE=1`, без флага | отказ, код 3, ничего не сделано | ок |
| `--yes` | отказ с подсказкой про `--force`, код 2 | ок |
| `--modules=nosuch` | код 2 со списком доступных | ок |
| настоящий `/dev/tty`, ответ `n` | отмена, `~/.bashrc` и снипеты нетронуты | ок |
| настоящий `/dev/tty`, ответ `y` | **не** подтверждение, ничего не удалено | ок |
| настоящий `/dev/tty`, ответ `yes` | выполняет, лаунчер и блоки `knrc:` исчезают | ок |
| `--modules=aliases --force` | откатывает только модуль; `~/.local/bin/knrc` и `~/.knrc.log` на месте | ок |
| повторный `--force` после полного отката | идемпотентно, без ошибок | ок |

Настоящий `/dev/tty` в контейнере получается через
`setsid -w script -qec "..." /dev/null < файл-с-ответом`: `docker run`
без `-t` контролирующего терминала не даёт вовсе, а без него проверялась
бы не та ветка кода.

Модули по умолчанию: `base zsh tmux aliases cli-tools git-config
ssh-config python-tools extras diagnostics fonts` — покрывают все виды
изменений, которые делает установка (копируемые конфиги с бэкапом,
rc-блоки, ключи git, бинарники в `/usr/local/bin` и `~/.local/bin`,
шрифты, смена login-shell). `nvim`, `docker` и `git-ecosystem` в набор
по умолчанию не входят: они самые долгие, а их откат — те же три вида
действий. Прогнать их можно явно, передав список вторым аргументом.
