# modules/docker.sh

Ставит Docker Engine + `docker compose` плагин через официальный скрипт
`get.docker.com` (сам определяет дистрибутив, поддерживает все 4
целевых); отдельно `docker-compose` не ставится, как и зафиксировано в
списке программ. После установки пытается `systemctl enable --now
docker` — best-effort, не валит модуль, если systemd недоступен
(актуально в контейнерах/некоторых WSL-конфигурациях, там `systemctl`
есть, но не функционирует без PID 1 = systemd; на реальной машине с
systemd отработает штатно).

## Добавление пользователя в группу docker

(запуск без `sudo`) — зафиксировано пользователем как решение
"спрашивать": та же схема, что у выбора shell'а в zsh.sh — вопрос через
`/dev/tty` (`docker::_want_user_in_group`), env-override
`DOCKER_ADD_USER_TO_GROUP=yes|no`, безопасный дефолт "no" без
интерактива (группа `docker` по факту эквивалентна root).

**Тестирование**: end-to-end на Ubuntu 24.04, Fedora (актуальная версия —
на Fedora 39 упал из-за того, что сам скрипт Docker считает её EOL и не
находит один из пакетов для неё; это ограничение апстрим-скрипта/образа,
не модуля), CentOS Stream 9: установка, идемпотентность, добавление в
группу по флагу и корректный пропуск без флага/tty (безопасный дефолт).

## Запись факта добавления в группу (2026-08-25)

`docker::configure_user_group` перед `usermod -aG docker` записывает
факт добавления через `state::record docker-group.added`
([scripts/lib/state.sh](../../scripts/lib/state.sh)).

Причина — `knrc uninstall` ([uninstall.md](uninstall.md)): по `id -nG`
видно только «состоит в группе», а состоял ли пользователь в ней до
установки — уже нет. Выводить из группы по факту членства значило бы
ломать окружение тому, кто добавил себя туда сам. Поэтому откат выводит
пользователя из группы docker **только** при наличии этой записи, а на
машинах, настроенных версией без записи состояния, просто пишет об этом
в отчёт «осталось».

Сама запись делается только в той ветке, где добавление реально
происходит, и уважает `DRY_RUN`.

## Выбор Docker Desktop / Docker Engine под WSL (2026-08-27)

`get.docker.com` сам детектит WSL и в этом случае просто печатает
предупреждение и ждёт `sleep 20` перед тем, как продолжить обычную
установку Docker Engine — в логе это выглядит как будто скрипт завис
(пользователь сообщил именно такую ситуацию: вывод обрывается на
середине строки `apt-get ... install d...`, хотя это просто буферизация
и скрипт продолжает работать).

Теперь модуль сам детектит WSL **до** запуска `get.docker.com`
(`os::is_wsl` в [os-detect.sh](../../scripts/lib/os-detect.sh) —
`WSL_DISTRO_NAME` или `microsoft` в `/proc/sys/kernel/osrelease`) и даёт
осознанно выбрать между:

- **Docker Engine внутри WSL** — как на обычном Linux, через тот же
  `get.docker.com` (20-секундная пауза апстрим-скрипта никуда не делась,
  но пользователь её уже ждёт осознанно, а не натыкается на неё
  случайно);
- **Docker Desktop** — ставится отдельно на Windows-хосте, модуль
  ничего не устанавливает и печатает пошаговую инструкцию
  (`docker::_print_wsl_desktop_instructions`): скачать Docker Desktop,
  включить WSL Integration для этого дистрибутива в его настройках,
  перезапустить WSL (`wsl --shutdown` из Windows), проверить `docker
  info` внутри WSL.

Тот же механизм конфигурации, что и у остальных интерактивных вопросов
в проекте: вопрос через `/dev/tty` (`docker::_ask_wsl_mode`),
env-override `DOCKER_WSL_MODE=desktop|engine`, безопасный дефолт
`engine` без интерактива (совпадает с прежним поведением скрипта до
появления выбора — идемпотентность и `NONINTERACTIVE=1` не меняются).

Выбор `desktop` — не ошибка: `docker::install_engine` просто
возвращает 0 без установки. Дальше по `docker::install` штатно
пропускаются `enable_service` (нет `docker.service`) и
`configure_user_group` (нет группы `docker`) — оба best-effort и не
валят модуль. `knrc doctor` в этом случае честно показывает бинарник
`docker` как отсутствующий, что и ожидается — Docker в этом случае
живёт на Windows-хосте, а не внутри WSL-дистрибутива.

**Тестирование**: `base,docker` на `debian12` — оба режима.
`DOCKER_WSL_MODE` не задан + `NONINTERACTIVE=1` (безопасный дефолт
`engine`) — контейнер Docker Desktop for Windows сам работает на
WSL2-ядре, так что `os::is_wsl` реально сработал в проверке; два
последовательных прогона в одном контейнере подтвердили и установку, и
идемпотентность (второй прогон видит уже установленный docker и
пропускает независимо от WSL-ветки). `DOCKER_WSL_MODE=desktop` —
установка Docker Engine пропущена, инструкция напечатана,
`knrc doctor --modules=docker` отработал без падения (бинарник помечен
как отсутствующий).

## Ложное "уже установлен" из-за podman-docker (2026-08-26)

Обнаружено на CentOS Stream в WSL: `/usr/bin/docker` уже существовал на
чистой машине, но не был Docker Engine — это шим из пакета
`podman-docker` (RHEL-семья ставит его по умолчанию на части образов;
symlink либо обёртка, транслирующая docker-команды в podman). Голая
проверка `command -v docker` принимала шим за "уже установлен" и
пропускала установку целиком — из-за чего дальше не было ни
`docker.service` (`Failed to enable unit, unit docker.service does not
exist`), ни группы `docker` (`usermod: group 'docker' does not exist`):
обе создаёт постинсталл настоящего `docker-ce`, которого модуль так и
не запустил.

Исправлено `docker::_is_podman_shim`: проверяет `readlink -f` на
бинарнике `docker` (ловит symlink-вариант шима) и вывод `docker
--version` (ловит вариант с обёрткой-скриптом, который печатает `podman
version ...`). Если шим найден, `docker::install_engine` сначала удаляет
пакет `podman-docker` через `PKG_MANAGER` (`apt`/`dnf`/`yum`), и только
после этого ставит настоящий Docker через `get.docker.com` — как и на
чистой машине без podman.
