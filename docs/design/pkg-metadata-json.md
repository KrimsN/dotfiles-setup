# Прототип: JSON-реестр способов установки пакетов

**Статус: ветка `design/pkg-metadata-json`.** Данные (`registry.json` +
`methods/*.json` + `*.schema.json`), диспетчер —
[scripts/lib/pkg-registry.sh](../../scripts/lib/pkg-registry.sh) — и
перенос модулей [cli-tools.sh](../modules/cli-tools.md),
[extras.sh](../modules/extras.md), [python-tools.sh](../modules/python-tools.md)
на вызов диспетчера реализованы, протестированы (юнит-тесты диспетчера +
интеграционный тест на заглушках — см. "Диспетчер: реализация и тесты"
ниже) и **подтверждены end-to-end** через `.claude/skills/test-module/`
на всех четырёх целевых дистрибутивах (Ubuntu 24.04, Debian 12, Fedora,
CentOS Stream 9, по два прогона на идемпотентность каждый — все чисто).
Легаси-путь (`cli::install_pkg_group`, `cli::fallback_*`,
`cli::install_eza`/`delta`/`curlie`/`zoxide` и прямые вызовы
`os::pkg_install`/`github_release::install` в `extras.sh`) удалён — вся
установка пакетов в этих трёх модулях теперь идёт через `pkg::install`.
Флаг `install.sh --package=NAME[:SOURCE]`
диспетчер уже поддерживает (`--source=`), но сам флаг в `install.sh` не
заведён.

## Зачем

Сейчас в [modules/cli-tools.sh](../../modules/cli-tools.sh) и
[modules/extras.sh](../../modules/extras.sh) для части пакетов (ripgrep, fd,
fzf, bat, jq, httpie, eza, delta, curlie, zoxide, fastfetch) развилка
"пакетный менеджер → GitHub → pip" реализована как набор bash-функций
(`cli::install_eza`, `cli::fallback_ripgrep`, ...) и `case` в `cli::fallback`.
Цель реестра — две вещи:

1. Не увеличивать шанс отсутствия пакета (то, что уже даёт текущий fallback —
   реестр не меняет эту гарантию, только делает её данными, а не кодом).
2. Дать install.sh возможность поставить конкретный пакет из конкретного
   источника (`--package=zoxide:github`), не трогая остальную установку.

## Разбиение на файлы: по способу установки, не по ОС

Изначальная версия не учитывала `uv`/`ruff` из
[modules/python-tools.sh](../../modules/python-tools.sh) — оба используют
способы установки, которых не было среди pkg/github/pip. Добавлены ниже
(см. "Ещё два способа установки").

- **[data/packages/registry.json](../../data/packages/registry.json)** —
  стратегия: порядок установки (порядок элементов массива `packages`),
  список методов на пакет с `priority` и `comment` (обоснование выбора,
  тот же текст можно показать в будущем интерфейсе выбора источника).
  Не содержит технических деталей метода (regex, имя пакета и т.п.).
- **data/packages/methods/{pkg,github,pip}.json** — технические детали
  каждого метода, по одному файлу на тип метода, ключ — имя пакета.

Разбиение по ОС (`os/debian.json`, `os/rhel.json`) рассматривали и
отклонили: реальное расхождение между дистрибутивами в проекте — только имя
пакета в `apt`/`dnf`/`yum` (и то на практике у нас оно везде совпадает,
кроме случая `fd` → `fd-find`, где совпадает **между** менеджерами, просто
отличается от имени инструмента). GitHub- и pip-методы от ОС не зависят
вообще. Разбиение по ОС продублировало бы repo/regex для github-пакетов в
файл каждого дистрибутива без всякой пользы — разбиение по методу дешевле и
честнее отражает, где на самом деле проходит граница различий.

## Как записан порядок и приоритет

- **Порядок установки пакетов** — просто порядок элементов массива
  `packages` в `registry.json` (JSON/`jq` сохраняют порядок ключей и
  элементов массива, отдельное числовое поле `order` не нужно — это был бы
  второй источник истины, который придётся синхронизировать с положением
  в массиве).
- **Приоритет методов внутри одного пакета** — массив `methods`, где каждый
  элемент несёт `priority` (число, для явности при выборке "предпочтительный
  метод для UI") и `comment` (человекочитаемое обоснование). Порядок в
  массиве и число `priority` сейчас избыточны (можно было бы обойтись только
  порядком массива) — оставлено явное число, потому что предполагаемый
  будущий флаг `--package=NAME:SOURCE` при отсутствии `SOURCE` должен уметь
  сослаться на "метод с priority=1", а не пересчитывать позицию в массиве.
- **`prereq`** (пример: `tldr` → `"prereq": "epel::ensure"`) — имя bash-функции,
  которую дозвонить перед установкой. Не смоделировано как generic JSON-граф
  зависимостей: `epel::ensure` — это включение репозитория, а не установка
  другого пакета из этого же реестра, разные по природе действия. Пусть
  остаётся ссылкой на существующую bash-функцию, а не отдельным DSL.

## Разные пути для разных репозиториев

`methods/github.json` — по одной записи на пакет с собственным `repo`,
`asset_regex`/`asset_by_arch`, `inner_path_glob`, `target_name`. Для
пакетов, где имя архитектуры в имени ассета совпадает с одним из двух
общих соглашений (`{arch_rust}`: x86_64/aarch64 → используется как есть;
`{arch_go}`: x86_64/aarch64 → amd64/arm64), используется `asset_regex` с
плейсхолдером, подставляемым из уже существующих
`github_release::arch_rust`/`arch_go`.

Для пакетов вне этих двух соглашений — `asset_by_arch` (прямое соответствие
`uname -m` → regex, без плейсхолдера). Реальный такой случай уже есть в
проекте: `fastfetch` называет ассет для ARM `aarch64`, а не `arm64`,
который вернула бы `arch_go` (см. [modules/extras.sh](../../modules/extras.sh):
`case "$(uname -m)"` вместо использования `arch_go`/`arch_rust`). Реестр
должен уметь выразить оба соглашения, а не только "стандартное" — иначе
`fastfetch` пришлось бы оставить как код-исключение прямо внутри
дженерик-диспетчера, что свело бы на нет саму идею декларативности.

## Проверка агентами (2026-08-25): что реально изменилось

Все 13 пакетов прогнаны через четыре параллельных агента (WebFetch реальных
GitHub Releases API + пакетных репозиториев дистрибутивов, а не по памяти).
Правки внесены прямо в `registry.json`/`methods/*.json`, здесь — сводка,
почему.

**Сломанные данные (не просто устаревшие — реально не работали бы):**
- **`eza`** — regex ссылался на `-unknown-linux-musl.tar.gz`, но проект
  перестал публиковать musl-сборки где-то между v0.22.0 и текущим v0.23.5.
  Старый regex не совпал бы ни с одним ассетом latest-релиза. Исправлено на
  `-unknown-linux-gnu.tar.gz` (не `_no_libgit`-вариант — тот без поддержки
  git-статуса).
- **`delta`** — у `aarch64` нет musl-сборки вообще, только `gnu` (у `x86_64`
  — musl есть). Единый `asset_regex` с одним плейсхолдером `{arch_rust}` для
  обеих архитектур физически не мог работать для aarch64. Переведено на
  `asset_by_arch` (как `fastfetch`) — ещё один довод в пользу того, что
  схема правильно предусмотрела оба варианта заранее.

**Смена приоритета метода (данные корректны, но порядок был не оптимален):**
- **`fzf`** — apt-версия в Ubuntu/Debian отстаёt от апстрима на несколько
  крупных релизов (0.44 vs 0.7x) — GitHub Releases переставлен на
  `priority=1`, pkg — на `priority=2` (плюс пометка, что в EPEL9 пакет
  доступен только с конца 2023 года).

**Пакеты, у которых появился метод, которого не было (был bucket "нет в
репах ни у кого", хотя это уже было не совсем так):**
- **`delta`** — есть `git-delta` в Fedora/EPEL9 (актуальная версия) —
  добавлен `pkg` как приоритет 1 для dnf/yum, GitHub остаётся приоритетом
  для apt.
- **`zoxide`** — есть в Ubuntu/Fedora штатно (в стабильном Debian —
  отсутствует, только sid/trixie) — добавлен `pkg` как приоритет 1, GitHub
  — fallback.
- Реальный вывод: захардкоженный комментарий в уже работающем
  [modules/cli-tools.sh](../../modules/cli-tools.sh) ("eza, delta, curlie,
  zoxide — их нет в стандартных репах") — неточен для delta/zoxide уже
  сегодня, не только в реестре. Это находка про сам production-код, не
  только про прототип; чинить сам `cli-tools.sh` — отдельная задача вне
  этой ветки, здесь только зафиксировано как открытый вопрос.

**Найдено, но не применено — решение за пользователем:**
- **`tldr`** — под одним именем пакета в разных дистрибутивах живут РАЗНЫЕ
  клиенты: Haskell (`tldr-hs`) на Debian/Ubuntu, Python — на Fedora/EPEL.
  Разное поведение (скорость, формат кэша) под одинаковым названием
  команды. Агент предлагает `tealdeer` (единообразный статичный
  Rust-бинарник, pkg+github) как замену. **Не применено автоматически** —
  `tldr` явно перечислен в списке программ CLAUDE.md как решение
  пользователя, менять его — не решение агента или моё. Зафиксировано в
  `comment` пакета `tldr` в реестре, финальное решение — за пользователем.

**Добавлено с оговоркой "не проверено вживую":**
- **`ruff`** — помимо `custom` (`uv tool install ruff`), у ruff есть
  собственные статические бинарники на GitHub (`astral-sh/ruff`), не
  зависящие от `uv` — добавлен как `priority=2` fallback. Структура архива
  (`inner_path_glob`) предположена по аналогии с другими cargo-dist-пакетами
  проекта, но не подтверждена реальной распаковкой — помечено `$note` в
  `methods/github.json`, требует проверки перед реализацией диспетчера.

**Не найдено ничего лучше существующей схемы:**
- `ripgrep`, `fd`, `bat`, `jq`, `fastfetch`, `curlie`, `uv` — все данные
  подтверждены точно как есть, включая нетривиальные детали (rename
  `fd-find`→`fdfind` — только на apt, не на dnf/yum; `fastfetch` musl-ассет
  вопреки названию не статический).

## Последний fallback: `source_url`

Помимо структурированных методов (`pkg`/`github`/`pip`/`curl-sh`/`custom`),
у каждого пакета в `registry.json` теперь есть поле **`source_url`** —
ссылка на апстрим-репозиторий. Это не метод установки (собирать из
исходников автоматически мы сознательно не стали — компиляторный тулчейн
противоречит цели "быстрое развёртывание одной командой", см. рассуждение
выше по проекту в целом), а человекочитаемая подсказка на тот случай, когда
**все** методы для пакета отвалились:

```bash
pkg::install() {
  local pkg="$1"
  # ... перебор методов по priority ...
  # если ни один не сработал:
  local source_url
  source_url="$(jq -r --arg p "$pkg" '.packages[] | select(.name==$p) | .source_url' "$REGISTRY")"
  log::err "pkg::install: не удалось установить '$pkg' ни одним известным способом"
  log::err "pkg::install: попробуйте вручную — исходники здесь: $source_url"
  return 1
}
```

Логика простая: диспетчер не решает за пользователя, как собирать из
исходников (не парсит README, не угадывает build-систему) — он просто даёт
точку входа для ручного вмешательства вместо голого "не удалось
установить X" без единой зацепки, куда смотреть дальше.

## Ещё два способа установки: `curl-sh` и `custom`

`uv` ставится не через пакетный менеджер и не через `github_release::install`
(даже несмотря на то, что это Rust-бинарник, как `eza`/`delta`/`zoxide`), а
через официальный установщик `astral.sh/uv/install.sh` — сознательное
решение пользователя (см. комментарий в `python-tools.sh`): это способ,
который рекомендует сам проект, и он умеет самообновляться (`uv self
update`). Для реестра это отдельный тип метода —
**[data/packages/methods/curl-sh.json](../../data/packages/methods/curl-sh.json)**:
`url` установщика, `env` (переменные окружения для инсталлера — например
`UV_INSTALL_DIR`, чтобы бинарник лёг в `$HOME/.local/bin`, а не туда, куда
установщик решит сам) и `check` (как определить, что пакет уже
установлен — единого соглашения вроде "бинарник в PATH с именем пакета"
тут нет, в отличие от `github`-метода). Значения в `env` могут содержать
bash-переменные (`$HOME`) — реестр это доверенный контент репозитория, не
пользовательский ввод, поэтому диспетчер расширяет такие значения обычной
параметрической подстановкой, а не безусловным `eval`.

`ruff` — более сложный случай: он не "устанавливается из источника", а
ставится через уже поставленный `uv` (`uv tool install ruff`). Это не
завести как четвёртый структурированный метод (что было бы за
"universal `run`-метод с произвольной командой в JSON" — а это по сути
возврат bash-кода, просто в виде строки внутри JSON, без выгоды типизации).
Вместо этого — тип `custom` с полем `handler`: именем уже существующей
bash-функции (`python_tools::install_ruff`), тот же принцип, что уже
использован для `prereq`. `custom` — осознанный люк для случаев, которые
честно не описываются декларативно, а не попытка притвориться, что всё
можно свести к данным.

Плюс к этому `ruff` — первый пример **`requires`** (не `prereq`): он
зависит не от системной предпосылки, а от другого пакета из этого же
реестра (`uv`). Порядок массива `packages` и так гарантирует, что `uv` идёт
раньше `ruff`, но `requires: ["uv"]` документирует это явно и защищает от
поломки, если кто-то в будущем переставит элементы массива не глядя на
скрытые зависимости.

### Механика `custom`: как диспетчер это выполнит

`custom` не хранит технических полей в `methods/custom.json` — единственная
техническая деталь (`handler`) лежит прямо в записи метода внутри
`registry.json`. Диспетчер не интерпретирует данные, а вызывает функцию по
имени — тот же принцип, что уже применён к `prereq` (`epel::ensure`), просто
для всего шага установки, а не только для предусловия:

```bash
pkg::_run_custom() {
  local handler="$1"
  if [ "${DRY_RUN:-0}" = "1" ]; then
    log::info "[dry-run] запустил бы custom-обработчик '$handler'"
    return 0
  fi
  if ! declare -F "$handler" >/dev/null 2>&1; then
    log::err "pkg::install: custom handler '$handler' не объявлен (модуль не подключён?)"
    return 1
  fi
  "$handler"
}
```

`declare -F` проверяет, что имя реально объявлено как функция, до вызова —
без `eval` строки целиком. `handler` берётся из доверенного файла репозитория
(не от пользователя), но проверка всё равно нужна как защита от опечатки
или несмонтированного модуля (например `cli-tools` дёрнул `ruff` до того,
как `python-tools.sh` был подключён `source`).

**Важный пробел, который custom обнажает**: `DRY_RUN` в остальных типах
перехватывается *внутри* трёх общих точек мутации (`os::pkg_install`,
`rcfile::upsert_block`, `github_release::install`, см. их правки в этой же
ветке разработки) — custom-обработчик эти точки может вообще не вызывать
(`python_tools::install_ruff` дёргает `uv tool install ruff` напрямую).
Поэтому для `custom` диспетчер не должен полагаться на то, что каждый
будущий `handler` сам умеет останавливаться в dry-run — он обязан **не
вызывать `handler` вообще** при `DRY_RUN=1`, только залогировать. То же
верно для идемпотентности: она не централизована, `handler` отвечает за
неё сам (как `python_tools::install_ruff` уже делает через `command -v
ruff`), реестр это не переизобретает.

## Схемы: `*.schema.json` и ключ `$schema`

Каждый файл данных (`registry.json`, `methods/{pkg,github,pip,curl-sh}.json`)
получил парную `<имя>.schema.json` (JSON Schema, диалект 2020-12 — не
draft-07: схемы используют `$defs`, а не `definitions` draft-07, поэтому
и диалект в `$schema` заявлен соответствующий, а не "притворяется" более
старым) и ссылку `"$schema": "<относительный путь>/<имя>.schema.json"` в
самом файле данных — это стандартный для JSON-инструментария приём (как в
`package.json`/`tsconfig.json`): редакторы (VSCode и т.п.) сами
подхватывают схему из этой ссылки и дают автодополнение/подсветку ошибок
прямо при правке, без отдельной настройки.

Схемы лежат отдельно от данных, в `data/packages/schemas/`, а не рядом с
файлами, которые они описывают: файлы данных (`registry.json`,
`methods/*.json`) — то, что пользователь может открыть и подстроить под
себя, а схемы — служебные, лезть в них незачем. Отсюда и разная глубина
относительного пути в `$schema`: из `registry.json` — `./schemas/...`, из
`methods/*.json` — `../schemas/...`.

Формализовано схемами то, что раньше было только в комментариях:
- `type` метода — фиксированный `enum` (`pkg`/`github`/`pip`/`curl-sh`/`custom`),
  опечатку в типе теперь ловит редактор, а не диспетчер в рантайме.
- Для `type: custom` — `handler` обязателен (`if`/`then` в схеме), это то
  же самое ограничение, которое иначе бы проверялось только в диспетчере
  через `declare -F`.
- Для `github`-метода — `oneOf(asset_regex, asset_by_arch)`: обе схемы
  запрещены одновременно и обе отсутствующие тоже запрещены — вскрытая
  агентами путаница ("оставили и regex, и by_arch одновременно") теперь
  невозможна по построению, не только по дисциплине автора правки.
- `additionalProperties: false` везде — опечатка в имени поля (например
  `intern_path_glob` вместо `inner_path_glob`) становится ошибкой схемы, а
  не молча игнорируемым мусорным ключом.

`ajv`/`ajv-cli` в этой песочнице недоступны офлайн (`npx --no-install`
отказал, сеть за пределами уже закэшированных пакетов не трогали
намеренно — не тащить новую npm-зависимость ради разовой проверки).
Вместо этого — ручной валидатор на голом `node` (без внешних пакетов),
реализующий ровно те правила, что объявлены в схемах (required/enum/
additionalProperties/oneOf/if-then), прогнан по всем реальным данным
(чисто) и по намеренно испорченной копии (поймал все три внесённые
поломки: лишнее поле, отсутствующий `handler`, `oneOf`-конфликт в
`github`-методе `eza`) — это подтверждает, что схемы не декоративные, а
действительно соответствуют форме данных.

Если в проекте когда-нибудь появится `jq`/Python в `scripts/lint.sh` для
других целей — валидацию можно будет заменить на настоящий JSON Schema
валидатор (`ajv-cli`, `check-jsonschema` и т.п.) вместо самодельного
скрипта; пока это не оправдано ради ~14 пакетов.

## Диспетчер: реализация и тесты

[scripts/lib/pkg-registry.sh](../../scripts/lib/pkg-registry.sh) — рабочая
реализация всего описанного выше. Публичная точка входа `pkg::install <name>
[--source=TYPE]`:

- без `--source` перебирает методы пакета по `priority` (через `jq
  'sort_by(.priority)'`), пока один не сработает;
- с `--source=TYPE` — только методы этого типа (для будущего
  `install.sh --package=NAME:SOURCE`);
- `prereq`/`requires` выполняются перед самим методом; `requires` вызывает
  `pkg::install` рекурсивно для зависимого пакета;
- защита от циклов в `requires` — `PKG_REGISTRY_IN_PROGRESS` (ассоциативный
  массив "сейчас устанавливается"), защита от повторной установки в рамках
  одного запуска — `PKG_REGISTRY_DONE` (кэш результата по имени пакета);
- если ни один метод не сработал — печатает `source_url` как ручной fallback
  (см. выше), возвращает 1.

Каждый тип метода — свой internal-раннер (`pkg_registry::_run_pkg/_run_github/
_run_pip/_run_curl_sh/_run_custom`), решения по `DRY_RUN`/идемпотентности
из более ранних разделов документа перенесены в код без изменений логики.

### Тестирование без реального Linux

В этой сессии нет доступного Linux-хоста (`bash -n`/`jq` в
Windows-песочнице есть, реального `apt`/`dnf` — нет), поэтому диспетчер
проверен через **юнит-тест с заглушками** (`os::pkg_try_install`,
`github_release::install`, `epel::ensure`, `python_tools::install_ruff`,
`curl` — все стабы вместо реальных вызовов) — 14 сценариев: выбор метода по
priority, подстановка `{arch_go}`/`{arch_rust}`, оба варианта
`asset_by_arch` (включая переопределение `uname` для эмуляции aarch64),
`prereq`, `requires` (в т.ч. рекурсивный вызов через реальный `curl-sh`-метод
uv), `--source`, fallback между методами, `DRY_RUN`, ошибки (неизвестный
пакет/источник, все методы отвалились), кэширование и защита от циклов
(на искусственно сконструированном зацикленном реестре в отдельном
временном каталоге). Все 14 — зелёные.

**Два найденных при тестировании класса багов, оба важны для понимания
поведения, но специфичны для среды разработки, не для целевых
дистрибутивов:**

1. **`\r` в значениях, прочитанных через `< <(jq ...) | while read`**. В
   этой Windows/git-bash песочнице process substitution (в отличие от
   обычной `$(...)`) утаскивает завершающий `\r` в прочитанное значение —
   `"uv"` из `requires` превращалось в `"uv\r"` и переставало совпадать с
   именем пакета в реестре. Добавлена защитная обрезка (`"${req%$'\r'}"`)
   в обоих местах диспетчера, где используется этот паттерн (`requires`,
   ключи `env` в `curl-sh`) — на реальном Linux это no-op, но не мешает.
2. **Мутация массива внутри стаба `curl()` терялась.** Левая часть пайпа
   (`curl ... | env ... sh`) выполняется в отдельном субшелле — типичная
   ловушка bash: `CALLS+=(...)` внутри такого стаба меняет только копию
   массива в субшелле и теряется, когда субшелл завершается. Тестовый стаб
   переписан на запись в файл (переживает субшелл) — это баг тестового
   харнесса, не диспетчера, но стоит зафиксировать как урок: разработчик,
   который будет писать похожие тесты в будущем, наткнётся на то же самое.

## Циклическая зависимость от `jq`

Реестр в JSON читается через `jq` — а `jq` сам есть пакет из этого же
реестра. Решение (проговорено в предыдущем обсуждении, здесь только
зафиксировано): `jq` ставится захардкоженно в `modules/base.sh` обычным
`os::pkg_install jq`, тем же способом, каким `install.sh` бутстрапит
`git`/`curl` до клонирования репозитория (единственный уже существующий в
проекте прецедент такого исключения). Модули, использующие реестр
(`cli-tools`, `extras`), всё равно обязаны сами проверять `command -v jq
|| os::pkg_install jq` перед чтением файла — потому что модули по
архитектуре проекта независимы и `base` не гарантированно запущен
(`DOTFILES_MODULES="cli-tools"` — документированный сценарий). Перенос в
`base` ускоряет обычный путь, но не отменяет защитную проверку в самом
модуле.

  коде `epel::ensure` вызывался один раз перед всей группой пакетов;
  исправлено в `registry.json`. Урок: миграция легаси-кода на декларативные
  данные — хороший способ найти расхождения, которые в императивном коде
  были неявными (один вызов "на весь блок") и легко потерялись бы при
  простом копировании логики без перепроверки.
- Схемы (`*.schema.json`) есть и описывают форму данных, но их пока
  проверяет только разовый node-скрипт из этого обсуждения, не встроенный
  в `scripts/lint.sh` шаг — CI сейчас не узнает о поломке данных
  автоматически. Нужно либо завести настоящий JSON Schema валидатор
  (`ajv-cli`/`check-jsonschema`) как dev-зависимость, либо перенести
  ручной валидатор в `scripts/` и подключить к `lint.sh`.
- В рантайме (bash-диспетчер) схемы не участвуют вообще — `jq` при
  обращении к отсутствующему полю вернёт `null`, диспетчер должен явно на
  это реагировать `log::err`, а не полагаться, что данные уже проверены
  схемой на этапе установки.
- Отдельный шаг `jq empty <file>` для проверки синтаксиса JSON в
  `scripts/lint.sh` (сейчас lint не знает про `data/packages/*.json`).
- Пересмотр категоризации `jq` в CLAUDE.md (сейчас — "CLI-инструменты
  нового поколения", после переноса в `base` потребует правки этого списка,
  зафиксированного пользователем).
- **Решение по `tldr` vs `tealdeer`** — требует явного ответа пользователя
  (см. "Проверка агентами" выше), не подразумевается по умолчанию.
- **Правка самого `modules/cli-tools.sh`** — комментарий там ("eza, delta,
  curlie, zoxide — их нет в стандартных репах") устарел для delta/zoxide
  независимо от этой ветки с реестром; это уже баг в реальном коде, не
  только в прототипе данных.
- **Официальный сторонний apt-репозиторий для `eza`** (`deb.gierens.de`,
  поддерживается мейнтейнерами самого проекта) — даёт актуальную версию на
  Debian/Ubuntu, но требует нового класса метода (добавление стороннего
  apt-источника + импорт GPG-ключа) — более высокая планка доверия, чем
  что-либо ещё в реестре (не просто "поставить пакет", а "довериться
  внешнему репозиторию апстрима"). Сознательно не добавлено, решение — за
  пользователем.
- **Гранулярность приоритета метода по конкретному пакетному менеджеру, не
  только по типу метода** — вскрыто на `delta` (надёжен на dnf/EPEL9,
  устарел на apt) и потенциально на других пакетах: сейчас один `pkg`-метод
  считается одинаково приоритетным независимо от того, `apt` это или `dnf`.
  Пока решается только текстом в `comment`, схема этого не моделирует
  структурно — стоит пересмотреть, если такое расхождение окажется частым,
  а не единичным случаем.
- **`.deb`/`.rpm`-ассеты, которые некоторые проекты (delta, curlie) теперь
  прикладывают прямо к GitHub-релизу** — альтернатива текущему
  tar.gz+`inner_path_glob`-извлечению, даёт видимость установленной версии
  штатному пакетному менеджеру (`dpkg -l`/`rpm -q`) без подключения
  стороннего репозитория. Не добавлено — отдельный подтип метода `github`,
  не критично для MVP.
